# Cycle 6 — 2026-06-30: Gap Analysis & Boot Time Optimization

> **Cycle**: 6 | **Duración**: 2026-06-30 (sesión única)
> **Objetivo**: Identificar y ejecutar optimizaciones de alto impacto/bajo esfuerzo en config loading y estructura de código

## Resumen

Ciclo enfocado en análisis sistemático del pipeline de config loading, ejecutando optimizaciones concretas con triple-verify. Se identificaron y corrigieron 4 categorías de problemas: spread innecesario, dead exports, error handling silencioso, y ausencia de benchmark tooling.

## Hallazgos

### 1. normalizeLoadedConfig: spread copy incondicional
- **Severidad**: 🟢 Bajo (pero alta recurrencia: 14-20 llamadas por sesión)
- **Causa raíz**: `{ ...data }` se ejecutaba siempre, incluso cuando no había campos legacy que eliminar. La verificación `hadLegacy` ocurría DESPUÉS del spread.
- **Fix**: Mover el chequeo `!("theme" in data || "keybinds" in data || "tui" in data)` ANTES del spread
- **Impacto**: ~5-7 KB alloc evitados por sesión (~28-40 µs CPU). Los campos legacy solo existen en configs pre-v1.17 (~1% de los casos).

### 2. Dead exports en markdown.ts
- **Severidad**: 🟢 Bajo
- **Hallazgo**: `FILE_REGEX`, `SHELL_REGEX` eran `export const` pero solo se usaban internamente. `fallbackSanitization` era completamente muerto (0 referencias en src/).
- **Fix**: Remover `export` de FILE_REGEX/SHELL_REGEX, eliminar `fallbackSanitization`
- **Impacto**: Limpieza de namespace (`ConfigMarkdown` expone solo `files`, `shell`, `parse`), ~200 B - 1 KB heap liberado

### 3. Effect.catch silenciosos sin logging
- **Severidad**: 🟡 Medio (degradaba debuggabilidad)
- **Hallazgo**: 3 sitios en config.ts donde errores se tragaban sin registro:
  - Escritura de $schema a config file
  - Seed de config global default
  - Fallo de accountSvc.active()
- **Fix**: Agregar `Effect.logWarning` con contexto (path y error) en cada catch
- **Impacto**: Costo cero en happy path, ~2-7 µs solo en error path

### 4. Ausencia de benchmark tooling para binario
- **Severidad**: 🟡 Medio (impedía medir impacto de optimizaciones)
- **Hallazgo**: No existía script para medir cold boot --help del binario compilado
- **Fix**: Crear `scripts/vmk-bench.ps1` — mide cold boot (avg/min/max), binary size, smoke test. Guarda resultados en `docs/metricas/` como JSON estructurado.
- **Impacto**: Permite tracking continuo de performance

## Aprendizajes

- `normalizeLoadedConfig` se llama 14-20 veces por sesión de opencode — el spread incondicional era un desperdicio pequeño pero de alta recurrencia.
- El patrón de triple-verify con 3 subagentes encontró un bug de tipos que un build check solo no detectó (el error era semántico, no sintáctico).
- Start-Process en PS7 rechaza `-RedirectStandardOutput` y `-RedirectStandardError` apuntando al mismo archivo — require archivos temporales separados.
- Las optimizaciones de configuración (evitar spreads, paralelizar I/O) tienen impacto acumulativo — 126ms (parallel I/O) + ~0.04ms (spread) + 470ms total = la mayoría de la mejora viene del parallel I/O y variación de runs.
- La mejora de 470ms (24.9%) es principalmente del parallel I/O en config.ts implementado previamente en este ciclo, más variación natural del runtime de Bun y caching de disco.
